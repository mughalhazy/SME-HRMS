## 1. Standard Response Envelope

Source: `D:\SaaS\HRMS\backend\api_contract.py`

All services that import `api_contract.py` use one of two top-level shapes. Services that do **not** use `api_contract.py` (compliance, banking, whatsapp, decision) produce a non-standard envelope — see Section 6.

### 1.1 Success Envelope

Produced by `success_payload()` / `success_response()`.

```json
{
  "status": "success",
  "data": <any>,
  "meta": {
    "request_id": "<uuid string>",
    "timestamp": "<ISO8601 UTC, e.g. 2026-06-15T10:00:00.000Z>",
    "pagination": {
      "limit": <int | null>,
      "cursor": <str | null>,
      "next_cursor": <str | null>,
      "count": <int | null>
    },
    "tenant_id": "<str>",
    "actor": {
      "id": "<str>",
      "type": "user | service",
      "role": "<str>"
    },
    "service": "<str>"
  },
  "error": null
}
```

**Field semantics:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `status` | `"success"` | Always | Literal string. |
| `data` | any | Always | Resource payload, list payload, or operation result. Empty object `{}` is used when no body applies. |
| `meta.request_id` | string | Always | Correlates to `X-Request-Id` / `trace_id`. Must be propagated end-to-end. |
| `meta.timestamp` | string (ISO8601) | Always | UTC, `Z` suffix. Generated by `_timestamp()` at response build time. |
| `meta.pagination` | object | Always | `{}` for non-list responses. For lists: `limit`, `cursor`, `next_cursor`, `count` fields. Default limit is 25, max 100 per `api-standards.md`. |
| `meta.tenant_id` | string | Conditional | Present when the handler provides a tenant context. |
| `meta.actor` | object | Conditional | Present when the handler provides actor context (`id`, `type`, `role`). |
| `meta.service` | string | Conditional | Service name string (e.g. `"leave-service"`). Present in most responses; not mandated by `api-standards.md` but emitted by all conforming `*_api.py` handlers. |
| `error` | null | Always on success | Always `null` on success responses. |

### 1.2 Error Envelope

Produced by `error_payload()` / `error_response()`.

```json
{
  "status": "error",
  "data": {},
  "meta": {
    "request_id": "<uuid string>",
    "timestamp": "<ISO8601 UTC>",
    "pagination": {}
  },
  "error": {
    "code": "STRING_ERROR_CODE",
    "message": "Human-readable message",
    "details": {} | [{"field": "...", "reason": "..."}] | null
  }
}
```

**Field semantics:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `status` | `"error"` | Always | Literal string. |
| `data` | `{}` | Always | Empty object on all error responses (enforced by `error_payload()`). |
| `meta` | object | Always | Same shape as success; `pagination` is always `{}` on errors. |
| `error.code` | string | Always | Machine-readable code from the error registry. See ERROR_CONTRACT.md. |
| `error.message` | string | Always | Human-readable description. |
| `error.details` | object or array | Always | Field-level validation detail when available. Defaults to `{}` (empty object) when not provided. Type is `dict[str, Any] \| list[dict[str, Any]] \| None`; `None` coerces to `{}`. This is a type inconsistency vs `api-standards.md` which implies only `{}`. |

### 1.3 List Payload Helper

`list_payload(items, *, extra=None, legacy_key=None)` produces:

```json
{
  "items": [...],
  "<legacy_key>": [...]
}
```

`legacy_key` is used by some handlers (leave) that also emit `"data"` for backward compat.

### 1.4 Pagination Payload

`pagination_payload(limit, cursor, next_cursor, count, extra=None)` produces:

```json
{
  "limit": <int | null>,
  "cursor": <str | null>,
  "next_cursor": <str | null>,
  "count": <int | null>
}
```

This object is always placed in `meta.pagination` by `meta_payload()`.

## 2. Versioning Convention

Source: `D:\SaaS\HRMS\backend\api-gateway\routes.py` (line 6), `D:\SaaS\HRMS\backend\docs\canon\api-standards.md` (§1, §9)

```python
API_VERSION_PREFIX = "/api/v1"
```

| Rule | Detail |
|---|---|
| Versioned prefix | All public routes are accessible via `/api/v1/<resource>` |
| Legacy bare-prefix | The gateway also resolves bare paths (`/<resource>`) and marks them `is_legacy_route = True`. Both forms are accepted. |
| Version major-only | Only major versions in the URL. Breaking envelope changes require a new major version or coordinated migration window. |
| Current version | `v1` (only version active) |

**Path translation**: `translate_to_upstream_path()` strips the `/api/v1` prefix before forwarding to the upstream service, unless `Route.expects_versioned_paths = True` (none of the 25 routes set this).

## 3. Authentication Contract

Source: `D:\SaaS\HRMS\backend\services\auth-service\api.py`, `D:\SaaS\HRMS\backend\docs\canon\api-standards.md` (§7)

### 3.1 General Rule

All endpoints are **authenticated by default** unless explicitly exempt. Authentication uses a JWT Bearer token.

```
Authorization: Bearer <token>
```

### 3.2 Exempt (Public) Endpoints

| Endpoint | Reason |
|---|---|
| `POST /api/v1/auth/login` | Credential exchange — issues token |
| `POST /api/v1/auth/refresh` | Refresh token exchange — no access token required |
| `POST /api/v1/auth/logout` | Revokes refresh token — uses refresh_token in body, not Bearer |

### 3.3 JWT-Authenticated Endpoints

All other endpoints require `Authorization: Bearer <token>`.

**In the auth service**: `get_auth_me` and `get_auth_session` explicitly check `authorization_header.startswith('Bearer ')` before proceeding. Missing or malformed headers return `401 TOKEN_INVALID`.

**In other services**: The `authorization` header is forwarded from the gateway as a parameter. `payroll_api.py` calls `service.decode_bearer_token(authorization)` to extract actor context. Other services (`leave`, `engagement`, `travel`, `helpdesk`, etc.) receive `actor_role` and `actor_employee_id` as already-extracted parameters because the gateway performs JWT validation and actor extraction before forwarding.

**Gateway-level JWT enforcement** (`backend/docker/api_gateway_service.py` lines 421–430): All requests are evaluated against `_AUTH_EXEMPT_PREFIXES = ("/health", "/ready", "/metrics", "/openapi.json", "/docs", "/api/v1/auth/")`. Requests outside these prefixes must carry `Authorization: Bearer <token>`. The gateway calls `verify_hs256_jwt(token, JWT_SECRET, audience=JWT_AUDIENCE, issuer=JWT_ISSUER)`. A missing or invalid token returns `401 UNAUTHORIZED` before the request is proxied to any upstream service.

**Gateway header propagation** (lines 468–471): After successful JWT verification the gateway extracts claims and forwards them to the upstream service as:

| Header | Source claim | Purpose |
|---|---|---|
| `X-User-Id` | JWT `sub` | Actor identity for audit / ownership checks |
| `X-User-Role` | JWT `role` | Role context for service-level RBAC decisions |
| `X-Tenant-Id` | JWT `tenant_id` | Tenant scoping for all multi-tenant data access |

These headers are the mechanism by which domain services receive the `actor_role`, `actor_id`, and `tenant_id` parameters used throughout their handler functions.

### 3.4 Error Codes for Auth Failures

| Scenario | HTTP Status | Error Code |
|---|---|---|
| Missing or malformed Bearer token | 401 | `TOKEN_INVALID` |
| Expired token | 401 | `TOKEN_EXPIRED` |
| Revoked token | 401 | `TOKEN_REVOKED` |
| Invalid credentials (login) | 401 | `INVALID_CREDENTIALS` |
| Disabled account | 403 | `ACCOUNT_DISABLED` |
| Authenticated but not authorized | 403 | `FORBIDDEN` |

### 3.5 Route-Level RBAC

Source: `backend/docker/api_gateway_service.py` — `_ROUTE_ROLE_MAP` (lines 66–71)

The gateway enforces role restrictions on specific route prefixes before proxying. A user whose JWT `role` claim is not in the allowed set receives `403 FORBIDDEN`. Routes not listed in `_ROUTE_ROLE_MAP` are accessible to any authenticated user.

| Route Prefix | Allowed Roles | Notes |
|---|---|---|
| `/api/v1/payroll` | `Admin`, `PayrollAdmin`, `Manager` | Payroll data access restricted |
| `/api/v1/audit` | `Admin` | Audit log is admin-only |
| `/api/v1/hiring` | `Admin`, `Manager`, `Recruiter` | Recruitment pipeline access |
| `/api/v1/reporting` | `Admin`, `Manager` | Analytics and reporting access |

All other routes allow any authenticated role. Role values are string-matched against the `role` claim in the JWT (`X-User-Role` header after extraction).
